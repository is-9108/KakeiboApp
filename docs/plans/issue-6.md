# issue-6 月次画面・収支フォーム

## 概要

認証後の仮ページを、月切替・収支一覧・月次集計・登録／編集共通フォームを備える月次画面へ置き換える。
既存のCRUD・集計APIと認証境界を再利用し、更新後は表示月の一覧・集計を再取得する。
日本語UIとレスポンシブ配置を実装し、375px・1280pxでの操作を実ブラウザの自動テストで検証する。

## 手順

1. **年月・フォーム入力の境界をテストして実装する。**
   - T1〜T3、T8〜T12の単体テストを先に追加する。
   - 初期表示月はJSTの現在月とし、年月の加減算は日付の月末補正に依存させない。APIの日付はYYYY-MM-DDのまま扱い、UTC変換で前日へずらさない。
   - 種別・カテゴリを`api/Models/Presets.cs`および要件4.3に合わせて定義する。種別変更時はカテゴリ選択を解除する。
   - 金額は未入力と0を区別して検証する。正の整数に加え、既存APIのint上限2,147,483,647円を超える値も送信前に案内する。独自の業務上限は追加しない。
2. **認証付きAPIクライアントをテストして拡張する。**
   - T18〜T21の通信テストを先に追加し、既存fetchEntriesの認証回帰テストも残す。
   - 一覧`GET /api/entries?month=YYYY-MM`、集計`GET /api/entries/summary?month=YYYY-MM`、登録`POST /api/entries/`、編集`PUT /api/entries/{id}`、削除`DELETE /api/entries/{id}`を提供する。
   - Bearerトークン取得、401とトークン更新失効の変換を共通化する。書き込みにはJSONヘッダー・本文を設定し、204ではJSON解析しない。
   - 400のValidationProblemは項目別メッセージとして扱う。非JSONの400や未知のエラー本文でも日本語の代替メッセージを表示できる形にする。
3. **月切替・一覧・集計を画面へ統合する。**
   - T1〜T7、T21〜T23の画面テストを先に書き、仮ページを置換する。
   - 月切替と一覧・集計の取得を一元化し、同じ取得世代の両結果が成功した時点で表示する。読み込み中は旧月データを新月の結果として表示しない。
   - 古い応答を無視する世代管理または同等の方式を採用し、アンマウント後や連続月切替時の上書きを防ぐ。認証オブジェクト全体の変更による不要な再取得も避ける。
   - 金額は日本円・桁区切り、構成比はAPI値を小数1桁の%として表示する。内訳は支出のみとし、クライアントで再集計・再丸めしない。APIの空の内訳に架空のカテゴリ行を追加しない。
   - 初期取得失敗時は再取得ボタンを用意する。ログアウト操作は正常・待機・エラー状態でも維持する。
4. **共通フォームと登録・編集をテストして実装する。**
   - T8〜T15、T19、T24、T25のフォーム・画面テストを先に追加する。
   - フォームは月次画面内に配置する。新規時の必須項目は未入力から操作できるものとし、種別・カテゴリには未選択状態を設ける。日付を含め、別月の収支も入力可能にする。
   - ラベルと入力欄を関連付け、エラーを入力欄に紐付ける。フォームは日本語の独自検証を行い、ブラウザ言語依存の標準エラーだけに頼らない。
   - 編集開始時は全既存値を設定し、編集キャンセルではAPIを呼ばず新規フォームへ戻す。更新処理中は保存・削除・月切替など競合する操作を無効化する。
   - 成功後はフォームを新規状態へ戻し、表示月を維持して一覧・集計を再取得する。別月へ日付を変更した場合も、現在表示月の結果を再取得する。
   - 保存失敗時は入力を保持する。更新成功後の再取得失敗は「保存済み・表示更新失敗」と区別し、古い結果を最新として扱わず、保存を再実行しない再取得導線を設ける。
5. **確認付き削除と更新の競合制御をテストして実装する。**
   - T16、T17、T22〜T25を追加・補完する。
   - 削除は`window.confirm`で日本語の確認文を表示し、キャンセル時はAPIも画面データも変更しない。確定後は削除成功を待ち、一覧・集計を再取得する。
   - 編集中の対象を削除できる構成の場合、削除成功後はその編集状態も解除する。
   - 連打による二重更新を防ぐ。401・トークン更新失効では既存のsignOutへ接続し、5xxや一時的な通信失敗ではログアウトしない。
6. **レスポンシブ表示とブラウザ自動テスト・CIを追加する。**
   - T26〜T28を先に作成し、375pxでは縦配置、1280pxでは一覧と集計・フォームを配置できるCSSを実装する。
   - Playwrightのテスト専用入口で実際のAppRoutes・AuthProviderを描画する。テスト専用Vite設定のaliasでamplifyAuth境界を代替し、実Cognitoを呼ばない。APIはブラウザのルートモックで月別データ・更新後データを返す。
   - 本番App・認証コードに認証迂回フラグを追加しない。通常のViteビルドではテスト入口・認証代替を使用しない。
   - CIのブラウザ用ジョブはNode.jsを用意し、`npm ci`、`npx playwright install --with-deps chromium`、`npm run test:e2e`を実行する。専用設定でViteを起動し、Docker内APIや実Cognitoに依存させない。
   - `frontend`で`npm test`、`npm run build`、`npm run test:e2e`を実行し、既存のAPIテスト（`docker compose run --rm api dotnet test Kakeibo.slnx`）も回帰確認する。
