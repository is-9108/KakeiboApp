## 分割方針

- **41 Issue（0〜40）**。番号は分割案のローカル番号であり、登録後のIssue番号ではない。
- 各Issueは1つの受け入れ可能な振る舞い。機能は小さなUI→API→永続化の縦切りとし、全DB層/全画面の横切りは行わない。初期雛形・契約・運用検証は独立した基盤/検証Issue。
- 規模はテストを含む差分でS=〜100行、M=〜300行。以下は見積り上限で、実装プラン時に超過が見込まれたら**着手前に再分割**し、Mの名前で大きな実装を通さない。受け入れ条件は各5個以下、テストプランは12件以下を目安にする。
- 初期機能は非公開環境でマージできる。段階的検証のため登録の基本保存と個別入力制約を分割するが、公開は全制約・セキュリティ・運用検証完了後のみ。未完成の機能を公開しない。
- 全IssueはMust。ラベルは候補であり、承認前に登録しない。

## 着手順と理由

1. **0を先行**。API/データ/エラー契約、所有範囲を確定し、異なる担当が互換性なく実装することを防ぐ。
2. 1の雛形を作り、2/4/5/8を分担。設計文書28/36は0後に並行着手できる。費用設計33は28後。
3. 2→3、3＋5→6、4＋5＋6→7。9後に10と13を並行可能。
4. 13後は11/12/14/15/16/17/18/23が並行候補。確定契約に従い、機能別ファイルと独立したテストを追加する。
5. 一覧18→19→20、集計23→24→25。編集21は入力制約完成後、削除22は一覧完成後。
6. 運用ログ26→API通知27、バックアップ29→30→31→32、費用33→34を別系列で進める。
7. セキュリティ35・性能37・スマホ38・PC39は必要な依存完成後、互いに並行可能。ただし負荷試験と操作試験は別環境または時間帯を分ける。
8. **40は最後**。全要件の証跡を照合してから公開を判断する。未達や相談中の項目があれば公開しない。

### 同時作業の共通注意

- 各Issueの「依存」が先行必須条件。契約0と基盤1で具体ファイルの所有者を決め、ルート設定・共通DTO・DBマイグレーション番号・IaCルートを無断で同時編集しない。
- 新マイグレーションはIssueごとに独立ファイルとし、番号/順序の割当てを調整する。共有スキーマ変更は後続担当へ通知し、契約変更が必要なら当該作業を止める。
- 14/15/16は同一検証器への変更が競合しやすい。0/1/13で項目別の拡張点とテスト配置を用意する。分離できない場合はこの3件を14→15→16の順で直列化する。
- 11/12/10は同じカテゴリ画面、18/21/22は同じ一覧画面を変更しやすい。機能別コンポーネント・ハンドラで分離し、共有ルートへの組込みは担当を一本化する。
- 17の再送識別は基礎スキーマ2・登録13で契約上の拡張点を用意する。保存本体や共通DTOを同時に書き換える必要が出た場合は13完了後、他の保存変更を直列化する。
- IaCはWeb、API、認証、ログ、バックアップ、通知を独立モジュールに分ける。ルート設定の変更は順序調整する。
- 32の復元は隔離DBを用い、37の性能試験は専用データを用いる。38/39の操作試験と共有DBを同時に書き換えない。
- 実現性・費用・性能が制約不適合の見込みなら該当Issueの実装前に相談し、独断でリージョンや機能を変更しない。

- 競合注意: 単独担当。後続が参照する唯一の契約を固定し、未決のまま実装へ渡さない。
- 受け入れ条件:
  - [ ] 機能ごとのJSON/REST契約、年月/ページ/エラー表現が文書化されている。
  - [ ] 物理データ関係、再送識別、順序、入力検証・集計表示の具体化が要件と整合する。
  - [ ] 機能別の所有ファイル/拡張点、マイグレーション・IaCの調整手順が記載されている。
  - [ ] 東京/.NET LTS/プール接続の対応状況を確認し、不適合見込みは相談事項として明示される。
- テスト観点: 要件との契約照合、別担当が独立実装できる接続点。
