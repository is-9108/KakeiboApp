# 独立レビュー手順

工程・承認ゲートは `docs/workflow.md`、レビュー担当の作業ルールは `CLAUDE.md` を参照する。
実装とは別の新しい Claude Code セッション（独立セッション）で実施する。再レビューも同様に、実装時の会話履歴・自己評価を引き継がない。`review-merge` スキルでは観点別サブエージェントで独立実行して統合する。利用できない場合や手動時は単独の独立セッションで3観点を確認してよく、縮退の理由を記録する。

## 1. 判断材料と差分の収集

1. Issue 番号を指定または `.ai/plan.md` から確認し、`gh issue view <番号>` と `gh issue view <番号> --comments` を読む。読めない場合は人間に内容を求める。
2. 判断材料は Issue、`.ai/plan.md`、`.ai/report.md`、`main` との差分の4点だけ。報告の主張は根拠となるコード・テストを読んで確かめる。
3. `git log --oneline main..HEAD`、`git status --short`、`git diff main --stat`、`git diff main` を実行する。未コミット差分も含め、`git ls-files --others --exclude-standard` で列挙した未追跡ファイルの内容も読む。対象ブランチ・コミット・確認時点を記録する。
4. 出力先は `.ai/review-<n>.md`。既存の最大番号に1を加え、なければ1とする。

レビュー中はコード・テスト・Git の状態を変更しない。書き込めるのは `.ai/` 配下の Markdown だけ。読み取り目的のテスト実行はよい。修正・commit・push・PR 作成はレビュー工程では行わない。

### 実施者とツール

Claude Code は利用できる場合、公式 `/code-review`（`--fix`・`--comment` は使わない）と `/security-review` を使う。使えない場合やレビュー本文が得られない場合は同じ観点で手動レビューする。テストの妥当性には対応する公式コマンドがないため、常に次節の観点で手動レビューする。公式コマンドの結果も §3 の検証対象で、根拠なしに採用しない。

この VM の非対話確認では `/security-review` は実行できたが、`/code-review low` は本文が得られず実質未確認。未コミット差分の取得は未確認。Agent ツールは非対話でサブエージェント1つによる読み取りタスクの実行のみ確認済み。プロジェクトスキルのスラッシュ呼び出しは、検証用コピーで `/plan-issue` の読み込みと前提不足での停止のみ確認済み（`.ai/plan.md` は未作成）。`/review-merge` の呼び出し実行、観点別サブエージェント3つの並列実行、`.ai/` への書き込みを伴う実行は未確認。詳細は `docs/claude-code.md`。結果が空でも差分なしとは断定せず、§1 の差分・未追跡ファイルを確認する。

## 2. 独立した3観点で確認する

### コード

- 各受け入れ条件を満たし、正常系・異常系・エッジケースで正しく動くか。
- Issue 範囲外や計画にない変更はないか。既存規約と一致するか。

### セキュリティ

次の変更があれば対象とし、実際の入力経路、権限、データの流れを追って確認する。

- 認証・認可・セッション
- 外部入力（フォーム、API、ファイル、URL、コマンド引数）
- DB クエリ、シェル・プロセス実行、ファイルシステムへのアクセス
- 秘密情報・暗号化・個人情報
- 外部サービスとの通信
- 依存パッケージの追加・更新

対象外でも理由を結果に記録する。特定ツールや数値スコアに依存せず、具体的な経路と根拠で指摘を判断する。

### テストの妥当性

コード・セキュリティとは独立した観点として、各受け入れ条件と重要な正常系・異常系・エッジケースをテストに対応付ける。

- 不足: 未検証の受け入れ条件・分岐・境界はないか。
- 過剰: 重複、要件と無関係、保守コストに見合わない過度なテストはないか。
- 妥当性: 実装内部ではなく要件・振る舞いを検証しているか。誤った実装で実際に失敗しうる検証か。

文書変更などでアプリのテストが対象外の場合も、その理由と代わりの検証の妥当性を確認する。

## 3. 指摘の検証・統合

1. すべての指摘候補を該当コード・テスト・文書と照合し、同じ問題は重複排除して1件にまとめる。観点別の生結果がある場合は全結果の完了を待ち、推測で先に統合しない。
2. 根拠があり対応可能な指摘だけを採用する。推測は「推測」と明記し、未確認の懸念は確認事項に分ける。好みを指摘しない。
3. 承認済みの設計どおり、発生経路を確認できない、好み、範囲外のリファクタリング・変更といった候補は不採用とし、理由を書く。承認された設計と受け入れ条件自体が矛盾する場合は独断で設計を変えず確認事項にする。
4. コード・テストの妥当性は C 系、セキュリティは S 系の ID を付ける。テストの妥当性は観点を明記し、レビュー回数はファイル名で区別する。
5. 重要度は高（不具合・脆弱性・受け入れ条件未達）、中（特定条件の問題・保守性・テストの不足や過剰、不適切な検証）、低（直す価値の明確な軽微な改善）とする。
6. 全受け入れ条件を1項目ずつ、差分と報告の検証結果で照合する。未実施・未検証は明記し、範囲外・計画外変更も報告する。

## 4. 保存と報告

以下のテンプレートで保存する。観点別の生結果がある場合だけ `.ai/review-<n>-<観点>.raw.md` に残す。必須の二重レビューは行わない。
人間だけが H3 で修正対象を選択する。Claude Code は未選択の `- [ ] 修正する` を出力し、`[x]` にしない。
チャットでは重要度別件数と結果のパスを伝え、未検証の受け入れ条件があれば1行で追記する。

```markdown
# Issue #<番号> レビュー結果（<n> 回目）

- 対象: <ブランチ> @ <コミットSHA>、<日付> 時点の main との差分
- 未コミット・未追跡ファイル: <有無と一覧>
- 判断材料: Issue、.ai/plan.md（状態）、.ai/report.md、main との差分
- 実施観点: コード、セキュリティ、テストの妥当性
- 独立性: 新規 Claude Code セッション、実装時の会話履歴・自己評価の非継承
- 生結果: <ある場合だけパス>

## サマリー
| 重要度 | 件数 |
|---|---|
| 高 | 0 |
| 中 | 0 |
| 低 | 0 |

セキュリティ指摘: <件数。上の重要度別件数の内数>
全体評価: <受け入れ条件の達成状況>

## 指摘
### C1 [中] <タイトル>

- [ ] 修正する
- 観点: <コード / テストの妥当性。セキュリティなら S 系 ID>
- 場所: <ファイル:行>
- 内容: <問題>
- 根拠: <確認箇所。推測なら明記>
- 影響: <入力・状態・結果>
- 推奨対応: <コードそのものは書かない>

## 受け入れ条件の確認
| 受け入れ条件 | 結果 | 根拠 |
|---|---|---|

計画との一致: <計画外・範囲外変更の有無>

## 確認事項（指摘ではない）
- <未実施検証、人間への確認>

## セキュリティレビュー
対象または対象外の理由: <理由>
結果: <確認観点・件数>

## 採用しなかった指摘
| 指摘 | 出どころ | 不採用理由 |
|---|---|---|
```

## 5. 修正・再レビューへの引き継ぎ

H3 で人間が選択した指摘だけを修正担当へ引き継ぐ。H3 承認範囲内で修正・検証・独立再レビューを自動反復できる。新規指摘は新たな H3 が必要。未対応指摘が残る間は push・Draft PR 作成に進まない。指摘ゼロで実装担当 Codex が人間の個別指示を待たずに push・Draft PR を自動作成し、マージは人間（H4）が行う。作業単位の明示的な禁止指示がある場合は従う。
