# issue #6 月次画面・収支フォーム

> PR #19・`origin/feat/issue-6-monthly-screen` は閲覧していません。以下は要件文書と `main` の基盤コードから独自に設計した案です。

## 1. 概要

ログイン後の仮ページ `AppHome` を月次画面に置き換える。既存の認証・ルーティングを維持し、次を同一画面に配置する。

- 前月・次月への切替
- 収入合計・支出合計・収支差額
- カテゴリ別の**支出**内訳（金額・構成比）
- 日付の新しい順の収支一覧
- 登録・編集で共用する収支フォーム
- 日本語の削除確認ダイアログ

一覧・集計は既存APIから取得し、登録・編集・削除の成功後に両方を再取得する。バックエンド、認証処理、新規依存ライブラリは変更しない。

## 2. 既存API仕様

確認元：認証導入済み `main` 基盤の `api/Endpoints/EntriesEndpoints.cs`、`api/Models/Presets.cs`、`api/Program.cs`、`frontend/src/api/client.ts`。いずれも現在のブランチに存在し、実物で再確認済み。

### エンドポイント

| 操作 | リクエスト | 成功時 |
| --- | --- | --- |
| 一覧 | `GET /api/entries?month=YYYY-MM` | 200、収支配列 |
| 集計 | `GET /api/entries/summary?month=YYYY-MM` | 200、月次集計 |
| 登録 | `POST /api/entries` | 201、登録済み収支。`Location`付き |
| 編集 | `PUT /api/entries/{id}` | 200、更新済み収支 |
| 削除 | `DELETE /api/entries/{id}` | 204、本文なし |

- `/api/*` はすべて認証必須。既存クライアントと同じく、取得したアクセストークンを `Authorization: Bearer ...` で送る。
- `month` は必須、厳密な `YYYY-MM`。未指定・不正形式は400。
- 一覧は指定月の月初から月末まで。並び順は **日付降順、同日付はID昇順**。
- PUTは全項目置換。編集・削除の対象が存在しない場合は404。
- 検証エラーは400。項目検証はValidationProblem、JSONバインド失敗も400となる。

### 収支

```ts
interface ApiEntry {
  id: number
  date: string       // YYYY-MM-DD
  type: string       // 収入 / 支出
  amount: number     // 1〜2147483647の整数
  category: string
  memo: string
}
```

POST・PUTは `id` 以外の項目を送る。日付・種別・金額・カテゴリは必須。メモは任意で、省略・nullは空文字として保存される。

カテゴリは種別ごとの固定プリセットであり、一覧取得APIは存在しない。

- 支出：外食費、食費、日用品、交通費、住居費、光熱費、通信費、趣味・娯楽、医療・健康、その他
- 収入：給与、副収入、その他

### 月次集計

```ts
interface MonthlySummary {
  month: string
  incomeTotal: number
  expenseTotal: number
  balance: number
  expenseBreakdown: {
    category: string
    amount: number
    percentage: number
  }[]
}
```

- 差額は収入合計−支出合計。
- 内訳は支出が存在するカテゴリのみ。金額降順、同額はカテゴリ名のordinal昇順。
- 構成比は支出合計に対する百分率を小数第1位まで四捨五入した値。
- 支出なしの場合は内訳が空配列。収支なしの場合は合計・差額がすべて0。
- 合計はAPI側で `int` 計算されている。既存の合計オーバーフロー制約は本issueでは変更しない。

| 画面の順序 | 見出し・ログアウト、月切替、集計、一覧、フォーム。スマホでも現在月と集計を先に確認できる順序とする |
| コンポーネント | `MonthNavigation`、`MonthlySummary`、`EntryList`、`EntryForm`、`DeleteEntryDialog` に分割。通信・画面状態は `AppHome` に集約する |

| フォーム | 常設の同一フォームを登録・編集で共用。「収支の登録」「収支の編集」で見出しを切り替える。編集開始時はフォームへスクロールし見出しへフォーカスする |

### 3.2 月・日付・表示形式

- 初期表示月は **JSTの現在月**。端末のローカルタイムゾーンに依存させない。
- 表示月は `YYYY-MM` 文字列で保持し、月の加減算は年・月で行う。年越しを扱い、APIの対応年範囲外へは移動させない。
- 月見出しは「2026年10月」、操作ボタンは「前月」「次月」とする。
- 日付値は `YYYY-MM-DD` のまま扱い、表示は「2026年10月28日」。UTCへの日時変換による日付ずれを避ける。
- 金額は日本語ロケールの桁区切り＋「円」。差額が負の場合は負号を維持する。
- 構成比はAPI値を再計算せず、小数第1位＋`%`で表示する。
- 支出内訳が空の場合は「支出の内訳はありません。」、一覧が空の場合は「この月の収支はありません。」とする。

### 3.3 状態管理・通信

- React標準のstate・effect・refを使用し、状態管理ライブラリは追加しない。
- 状態は表示月、一覧・集計の取得状態、登録／編集モード、フォーム値、削除対象、更新処理状態、通知・エラーに分ける。
- `fetchEntries` に加えて、集計取得・登録・編集・削除関数を既存APIクライアントへ追加する。
- 認証ヘッダー付与・401判定・refresh token失効判定は共通化し、既存の挙動を維持する。
- 一覧と集計は同じ月で並行取得し、**両方成功した場合のみ一組として表示**する。読み込み中や失敗時に、別月のデータ・古い集計を現在月の値として表示しない。
- リクエスト世代番号で、月切替前の遅延レスポンスが最新画面を上書きしないようにする。アンマウント後も状態更新しない。
- 登録・編集・削除成功後は、表示月の一覧・集計を再取得する。楽観的更新は行わず、APIを正とする。
- 保存日付が表示月の外でも送信を認める。表示月は自動変更せず、表示中の月を再取得する。対象月へ切り替えれば保存内容を確認できる。
- 月切替だけでは入力中のフォームを破棄しない。保存先はフォームの日付であることを案内する。
- 更新要求中は月切替・他の更新操作・フォーム再送信を無効化する。同期的な処理中ガードも設け、連打で要求が重複しないようにする。

### 3.4 フォーム初期値・入力検証

| 項目 | 決定と理由 |
| --- | --- |
| 新規の初期値 | 日付は表示月が現在月ならJSTの今日、それ以外は表示月の1日。種別は「支出」、金額・カテゴリ・メモは空。入力負担を下げつつ、カテゴリの意図しない選択を防ぐ |
| 編集の初期値 | 選択行の全項目をそのまま設定。単一件取得APIは追加しない |
| 必須検証 | 日付・種別・金額・カテゴリの空欄を送信前に検出し、該当項目に日本語エラーを表示する |
| 日付 | 実在する `YYYY-MM-DD`、年は0001〜9999。未来日や表示月外の日付は独自に禁止しない |
| 金額入力 | `type="text"` と `inputMode="numeric"` を使用。入力文字列を保持し、空欄や小数を丸めず検出する |
| 金額検証 | 半角数字のみ、数値として1〜2147483647の整数。0・負数・小数表記・指数表記・カンマ等は拒否。先頭ゼロは許容し、送信時に数値化する |
| 種別・カテゴリ | selectで選択。種別は「収入」「支出」、カテゴリは対応プリセットのみ。種別変更時はカテゴリを未選択へ戻す |
| メモ | 任意。独自の文字数制限・自動trimは追加しない。空欄は空文字で送る |
| 検証タイミング | 送信時に一括検証。登録・編集で同じ検証関数を使用する |
| エラーの読み上げ | label、`aria-invalid`、`aria-describedby`を付け、先頭の不正項目へフォーカスする |
| ブラウザ標準検証 | `noValidate`で標準バルーンに依存せず、日本語エラーをアプリ内に統一する |
| 成功／キャンセル | 保存成功後は新規フォームへ戻す。編集キャンセルはAPIを呼ばず、表示月に対応した新規初期値へ戻す |

プリセットはフロント側の定数として保持する。API側との重複は既存の「カテゴリAPIなし」という契約に合わせたもので、テストで値を固定する。

### 3.5 文言・エラー表示

- 見出し、項目名、操作、状態表示、確認・エラー・成功通知は日本語で統一する。
- 項目エラー例：
  - 「日付を入力してください。」
  - 「種別を選択してください。」
  - 「金額を入力してください。」
  - 「金額は1円以上の整数で入力してください。」
  - 「金額は2,147,483,647円以下で入力してください。」
  - 「カテゴリを選択してください。」
- 取得失敗は画面内に「月次データを取得できませんでした。」と「再読み込み」を表示する。
- 更新失敗はフォームまたは削除ダイアログに表示し、入力・対象を保持する。
- 400の項目別エラーは既知の項目キーを日本語メッセージへ対応付ける。未知のエラー・英語のProblemDetails・例外本文は直接表示しない。
- 404は「対象の収支が見つかりません。再読み込みしてください。」と表示する。
- 保存成功後の再取得だけ失敗した場合は「保存は完了しましたが、表示の更新に失敗しました。」など、処理成功と表示失敗を区別する。再読み込みでGETのみを再実行し、更新要求を再送しない。
- 401・refresh token失効は既存のログアウト処理を通してログイン画面へ戻す。通信失敗・500・403は認証失効とみなさない。
- 更新要求の自動リトライは行わない。通信断ではサーバー側で処理済みの可能性があるため、結果確認を促す。

### 3.6 レスポンシブ対応

- モバイルファーストのCSSとし、375pxでは全領域を縦1列にする。
- 900px以上では一覧とフォームを2列にし、集計はその上へ配置する。
- 固定幅を避け、Gridには`minmax(0, 1fr)`、子要素には`min-width: 0`を使用する。
- 入力・ダイアログは親幅以内に収め、長いメモ・改行のない文字列は折り返す。
- 操作ボタンは原則44px以上の高さとし、小さい画面でも押しやすくする。
- 横スクロールを単に隠すのではなく、長文・最大金額を含む実ブラウザ検証で発生しないことを確認する。

### 3.7 テスト戦略

- 既存のVitest・Testing Library・`fireEvent`を使用し、テスト依存は追加しない。
- APIクライアントはfetchと認証SDK境界をモックして通信契約を検証する。
- 画面結合テストではAPIクライアントをモックし、操作→送信→一覧・集計の再取得→表示更新を検証する。
- JST・年越し・入力検証は純粋関数の単体テストにする。
- 認証統合テストは仮ページの期待値を月次画面に更新し、既存のログイン・初回パスワード変更・ログアウト・認証失効の検証を残す。
- jsdomではレイアウトを証明できないため、375px・1280pxの操作と横スクロールは実ブラウザで手動検証する。結果を`review.md`に記録する。
