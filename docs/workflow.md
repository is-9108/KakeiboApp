# 開発フロー

Claude Code と Codex が共有する開発フロー。
エージェントごとのルールは `CLAUDE.md`（Claude Code）と `AGENTS.md`（Codex）に書く。

## 原則

- **役割分担**: Claude は要件定義・計画・レビュー、Codex は実装・テスト・修正を担当する。
- **人間が判断する**: 承認ポイント（H1〜H4）では、人間の明示的な承認なしに次へ進まない。
- **ファイルで引き継ぐ**: 他のエージェントの会話履歴に依存しない。必要な情報は GitHub Issue と `.ai/` の Markdown に書く。チャットで決まったことも、必ずファイルに反映する。
- **自動ループしない**: 各工程は人間の指示で開始する。レビュー → 修正 → 再レビューを自動で繰り返さない。
- **1 Issue = 1 Worktree = 1 ブランチ = 1 PR**。
- **止まって確認する**: Issue 範囲外の変更や設計変更が必要になったら、作業を止めて人間に確認する。

全体での禁止事項:

- main（デフォルトブランチ）への直接 commit / push
- force push、push 済み履歴の書き換え
- PR のマージ（マージは人間が行う）

## 全体像

| # | 工程 | 担当 | 成果物 | 承認 |
|---|------|------|--------|------|
| 1 | 要望を伝える | 人間 | — | |
| 2 | 要件の具体化 | Claude | Issue 案 | **H1** 要件 |
| 3 | Issue 作成 | Claude | GitHub Issue | |
| 4 | Worktree 作成 | 人間 | Issue 専用 Worktree | |
| 5 | 実装計画・テスト計画 | Claude | `.ai/plan.md` | **H2** 計画 |
| 6 | TDD 実装・自己検証 | Codex | コミット、`.ai/report.md` | |
| 7 | コードレビュー・セキュリティレビュー | Claude | `.ai/review-1.md` | **H3** 修正対象 |
| 8 | 承認済み指摘の修正・テスト | Codex | コミット、`.ai/report.md` に追記 | |
| 9 | PR 作成・最終確認 | Codex / 人間 | Draft PR | **H4** PR・マージ |

## 引き継ぎ情報の置き場所

| 情報 | 置き場所 | 書く人 |
|------|----------|--------|
| 要件・受け入れ条件 | GitHub Issue 本文 | Claude（H1 の後） |
| 実装計画・テスト計画 | `.ai/plan.md` | Claude |
| 実装・修正の報告 | `.ai/report.md` | Codex |
| レビュー結果 | `.ai/review-<n>.md` | Claude（修正するかどうかは人間が決める） |
| 最終的な検証結果 | PR 本文 | Codex |

- `.ai/` は Issue Worktree の直下に置き、`.gitignore` で Git の管理外にする。
- Worktree を削除すると `.ai/` も消える。残したい内容は Issue コメントか PR 本文に書く。

## 1. 要件定義フロー（工程 1〜3）

Worktree はまだ作らず、メインのチェックアウトで行う。Claude はファイルを変更しない。

1. 人間が Claude に要望を伝える。
2. Claude は既存コードを確認し、質問で要件を具体化する。
3. Claude が下記のテンプレートで Issue 案を提示する。
4. **H1**: 人間が Issue 案を承認する。
5. Claude が `gh issue create` で Issue を作成する。

要望が大きい場合は、1 PR でレビューできる大きさの複数の Issue に分割する。

Issue テンプレート:

```markdown
## 背景・目的
## 要件
## 受け入れ条件
- [ ] （検証可能な条件）
## 範囲外
## 制約・前提
## 未決事項
```

## 2. GitHub Issue と Worktree の運用（工程 4）

- ブランチ名: `issue-<番号>-<短い説明>`（例: `issue-12-login-form`）
- 作成方法: Orca の Worktree 作成機能を使う。CLI で作る場合は以下のとおり。

  ```sh
  git fetch origin
  git worktree add -b issue-12-login-form ../<repo>-issue-12 origin/main
  ```

- 以降の Claude と Codex の作業は、すべてこの Worktree で行う。
- `.ai/plan.md` を Worktree 内に置くため、Worktree は計画の作成前に作る。
- PR がマージまたはクローズされたら、人間が Worktree を削除する（`git worktree remove`）。

## 3. 実装計画フロー（工程 5）

1. Claude が Issue と関連コードを読み、`.ai/plan.md` に実装計画とテスト計画を書く。
2. **H2**: 人間が両方の計画をまとめて確認し、承認する。
3. 承認されたら、Claude が `状態:` を `承認済み (YYYY-MM-DD)` に更新する。

`.ai/plan.md` テンプレート:

```markdown
# Issue #<番号> 実装計画・テスト計画
状態: 承認待ち

## 方針
（採用するアプローチと理由。検討して採用しなかった案があれば一行で）

## 変更予定ファイル
- path/to/file — 変更内容

## 実装ステップ
1.

## テスト計画
| 受け入れ条件 | テスト内容 | 種別（unit / integration / e2e / 手動） |
|---|---|---|

## リスク・確認事項
```

## 4. TDD 実装フロー（工程 6）

1. Codex は `.ai/plan.md` の状態が `承認済み` であることを確認してから着手する。
2. テスト計画の項目ごとに Red → Green → Refactor を繰り返す。
   - Red: 失敗するテストを書き、失敗することを確認する。
   - Green: テストが通る最小限の実装をする。
   - Refactor: テストが通ったまま整理する。
3. 意味のある単位で Issue ブランチにコミットする。
4. 自己検証として、テスト全体・lint・型チェックを実行する。
5. 結果を `.ai/report.md` に書く。

`.ai/report.md` テンプレート:

```markdown
# Issue #<番号> 実装報告

## 実施内容
## 変更ファイル
## テスト結果
（実行したコマンドと結果。失敗やスキップも書く）
## 計画との差分
（なければ「なし」）
## 未解決事項・確認事項
```

修正（工程 8）の後は、同じファイルに `## 修正報告（review-<n>）` を追記する。

## 5. レビューフロー（工程 7）

1. 人間の指示で、Claude がレビューを開始する。新しいセッションで行うのが望ましい。
2. 入力は次の 4 つだけ。Codex の会話履歴は使わない。
   - Issue
   - `.ai/plan.md`
   - `.ai/report.md`
   - `main` との差分
3. コードレビュー: 利用できる場合は公式の `/code-review` を使う。
4. セキュリティレビュー: 下記の条件に当てはまる場合に、公式の `/security-review` で行う。
5. 結果を `.ai/review-<n>.md` に保存する（`n` は 1 から始まるレビュー回数）。
6. **H3**: 人間が、修正する指摘のチェックボックスに `[x]` を付ける。

レビュー中は、コード・テスト・Git の状態を変更しない。

セキュリティレビューが必要な変更:

- 認証、認可、セッション
- 外部入力の処理（フォーム、API、ファイル、URL、コマンド引数）
- DB クエリ、シェル・プロセスの実行、ファイルシステムへのアクセス
- 秘密情報、暗号化、個人情報
- 外部サービスとの通信
- 依存パッケージの追加・更新

当てはまらない場合は、レビュー結果に「セキュリティレビュー: 対象外（理由）」と書く。

`.ai/review-<n>.md` テンプレート:

```markdown
# Issue #<番号> レビュー <n> 回目
対象: <ブランチ> @ <コミットSHA>

## サマリー
（全体評価。指摘の件数（重要度別）。セキュリティレビューを実施したか、対象外ならその理由）

## 指摘
### C1 [高] タイトル
- [ ] 修正する
- 場所: path/to/file:行
- 内容:
- 根拠:
- 修正案:

### S1 [中] タイトル（セキュリティ）
- [ ] 修正する
- ...
```

- ID の接頭辞: `C` はコードレビュー、`S` はセキュリティレビュー。
- 重要度:
  - 高: 不具合・脆弱性・受け入れ条件の未達
  - 中: 保守性・テスト不足
  - 低: 軽微な改善
- 人間は、修正しない指摘に一言コメントを書いてよい（例: `対応しない: 別 Issue にする`）。

## 6. 指摘修正フロー（工程 8）

1. Codex は `.ai/review-<n>.md` のうち、`[x]` が付いた指摘だけを修正する。
2. チェックのない指摘には手を付けない。
3. 指摘ごとにコミットする。メッセージに ID を含める（例: `fix: C1 空入力時の例外を修正`）。
4. 修正に設計変更が必要な場合は、修正せずに止まって人間に確認する。
5. テスト全体を実行し、`.ai/report.md` に修正報告を追記する。

再レビューは、人間が指示した場合だけ行う。そのときは修正差分を中心に見て、`review-<n+1>.md` に書く。
2 回目のレビューの後も指摘が残る場合は、続けるかどうかを人間が決める。

## 7. PR と完了（工程 9）

1. 人間の指示で、Codex がブランチを push し、Draft PR を作成する。
2. PR 本文には次の内容を書く。
   - `Closes #<番号>`
   - 変更概要
   - テスト結果
   - 対応したレビュー指摘の ID
   - 対応しなかった指摘とその理由
3. **H4**: 人間が PR と検証結果を確認し、マージする。

## 人間の承認ポイント

| ID | タイミング | 人間が確認すること | 承認の残し方 |
|----|-----------|-------------------|-------------|
| H1 | Issue 作成前 | 要件・受け入れ条件・範囲外 | Claude に作成を指示する |
| H2 | 実装前 | 実装計画とテスト計画（まとめて確認） | Claude に承認を伝える → `状態: 承認済み` |
| H3 | 修正前 | どの指摘を修正するか | `review-<n>.md` に `[x]` を付ける |
| H4 | マージ前 | PR・テスト結果 | 人間が自分でマージする |

上記以外に、エージェントが止まって確認を求めたときも人間が判断する（範囲外の変更、設計変更、依存の追加など）。
