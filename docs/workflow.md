# 開発フロー

Codex が全作業工程を担当する開発フロー。作業ルールは `AGENTS.md`、独立レビューの具体的手順は `docs/review.md` に書く。Muse は起動・進行管理、人間は要望提示と承認・マージを担当する。

## 原則

- **役割分担**: Codex は要件定義・計画・実装・テスト・修正・独立レビューを担当する。
- **人間が判断する**: 承認ポイント（H1〜H4）では、人間の明示的な承認なしに次へ進まない。
- **ファイルで引き継ぐ**: 他のエージェントの会話履歴に依存しない。必要な情報は GitHub Issue と `.ai/` の Markdown に書く。チャットで決まったことも、必ずファイルに反映する。
- **承認範囲内で自動実行する**: 記録された承認に基づき、Muse の定常指示で各工程を起動できる。定常指示や時間経過は承認を代替しない。H2 承認済み計画の実装と、H3 承認済み指摘の修正・検証・独立再レビューを自動反復する。新規指摘は新たな H3 を待つ。
- **1 Issue = 1 Worktree = 1 ブランチ = 1 PR**。
- **止まって確認する**: Issue 範囲外の変更や設計変更が必要になったら、作業を止めて人間に確認する。

全体での禁止事項:

- main（デフォルトブランチ）への直接 commit / push
- force push、push 済み履歴の書き換え
- PR のマージ（マージは人間が行う）

## 全体像

| # | 工程 | 担当 | 成果物 | 承認 |
|---|------|------|--------|------|
| 1 | 要望を伝える | 人間 | — | |
| 2 | 要件の具体化 | Codex | Issue 案 | **H1** 要件 |
| 3 | Issue 作成 | Codex | GitHub Issue | |
| 4 | Worktree 作成 | Codex | Issue 専用 Worktree | |
| 5 | 実装計画・テスト計画 | Codex | `.ai/plan.md` | **H2** 計画 |
| 6 | TDD 実装・自己検証 | Codex | コミット、`.ai/report.md` | |
| 7 | 独立レビュー（コード・セキュリティ・テストの妥当性） | Codex | `.ai/review-1.md` | **H3** 修正対象 |
| 8 | 承認済み指摘の修正・テスト | Codex | コミット、`.ai/report.md` に追記 | |
| 9 | PR 作成・最終確認 | Codex / 人間 | Draft PR | **H4** PR・マージ |

## 引き継ぎ情報の置き場所

| 情報 | 置き場所 | 書く人 |
|------|----------|--------|
| 要件・受け入れ条件 | GitHub Issue 本文 | Codex（H1 の後） |
| 実装計画・テスト計画 | `.ai/plan.md` | Codex |
| 実装・修正の報告 | `.ai/report.md` | Codex |
| レビュー結果 | `.ai/review-<n>.md` | Codex（修正するかどうかは人間が決める） |
| 最終的な検証結果 | PR 本文 | Codex |

- `.ai/` は Issue Worktree の直下に置き、`.gitignore` で Git の管理外にする。
- Worktree を削除すると `.ai/` も消える。残したい内容は Issue コメントか PR 本文に書く。

## 1. 要件定義フロー（工程 1〜3）

Worktree はまだ作らず、メインのチェックアウトで行う。Codex はコード変更・commit・push をしない。

1. 人間が Codex に要望を伝える。
2. Codex は既存コードで実現可能性と影響範囲を確認する。不明点は推測で埋めず、少数の質問に選択肢と推奨案を付けて具体化する。
3. Codex が下記のテンプレートで Issue 案を提示する。
4. **H1**: 人間が Issue 案を承認する。
5. H1 の明示的承認後にだけ、Codex が `gh issue create` で Issue を作成する。

要望が大きい場合は、1 PR でレビューできる大きさの複数の Issue に分割する。

Issue テンプレート:

```markdown
## 背景・目的
## 要件
## 受け入れ条件
- [ ] （検証可能な条件）
## 範囲外
## 制約・前提
## 未決事項
```

## 2. GitHub Issue と Worktree の運用（工程 4）

- ブランチ名: `issue-<番号>-<短い説明>`（例: `issue-12-login-form`）
- 作成方法: Orca の Worktree 作成機能を使う。CLI で作る場合は以下のとおり。

  ```sh
  git fetch origin
  git worktree add -b issue-12-login-form ../<repo>-issue-12 origin/main
  ```

- 以降の Codex の作業は、すべてこの Worktree で行う。
- `.ai/plan.md` を Worktree 内に置くため、Worktree は計画の作成前に作る。
- PR がマージまたはクローズされたら、人間が Worktree を削除する（`git worktree remove`）。

## 3. 実装計画フロー（工程 5）

1. Codex が Issue 本文・承認コメントと専用 Worktree・Issue ブランチを確認し、関連コードを読み、`.ai/plan.md` に実装計画とテスト計画を書く。
   - 変更ファイル・手順・テストケースを会話履歴なしで実装できる粒度にする。コードそのものは書かず、全受け入れ条件をテスト計画に対応付ける。計画作成時点では承認済み状態を要求しない。
2. **H2**: 人間が両方の計画をまとめて確認し、承認する。
3. 人間が明示的に承認したときだけ、Codex が `状態:` を `承認済み (YYYY-MM-DD)` に更新する。

`.ai/plan.md` テンプレート:

```markdown
# Issue #<番号> 実装計画・テスト計画
状態: 承認待ち

## 方針
（採用するアプローチと理由。検討して採用しなかった案があれば一行で）

## 変更予定ファイル
- path/to/file — 変更内容

## 実装ステップ
1.

## テスト計画
| 受け入れ条件 | テスト内容 | 種別（unit / integration / e2e / 手動） |
|---|---|---|

## リスク・確認事項
```

## 4. TDD 実装フロー（工程 6）

1. Codex は `.ai/plan.md` の状態が `承認済み` であることを確認してから着手する。
   - Issue 本文・承認コメント、専用 Worktree・ブランチも確認する。実装担当は計画の不備・矛盾を独断で変更せず報告する。変更前にテストを実行して既存失敗を記録する。
2. テスト計画の項目ごとに Red → Green → Refactor を繰り返す。
   - Red: 失敗するテストを書き、失敗することを確認する。
   - Green: テストが通る最小限の実装をする。
   - Refactor: テストが通ったまま整理する。
3. 意味のある単位で Issue ブランチにコミットする。
4. 自己検証として、テスト全体・lint・型チェックを実行する。
5. 結果を `.ai/report.md` に書く。

`.ai/report.md` テンプレート:

```markdown
# Issue #<番号> 実装報告

## 実施内容
## 変更ファイル
## テスト結果
（実行したコマンドと結果。失敗やスキップも書く）
## 計画との差分
（なければ「なし」）
## 未解決事項・確認事項
```

修正（工程 8）の後は、同じファイルに `## 修正報告（review-<n>）` を追記する。

## 5. レビューフロー（工程 7）

1. 実装・自己検証後、実装とは別の新しい Codex セッションで独立レビューを開始する。会話履歴・自己評価は引き継がず、再レビューも同じ独立性を守る。
2. 判断材料は Issue、`.ai/plan.md`、`.ai/report.md`、`main` との差分の4点だけ。根拠確認のためコード・テストを読み、未コミット・未追跡差分も含める。
3. `docs/review.md` に従い、コード・セキュリティ・テストの妥当性を独立した3観点として確認する。単独の独立セッションでよく、並列レビューは必須ではない。
   - コード: 受け入れ条件、動作、エッジケース、範囲、規約。
   - セキュリティ: 認証・認可・セッション、外部入力、DB クエリ、シェル・プロセス実行、ファイルシステム、秘密情報・暗号化・個人情報、外部通信、依存追加・更新。対象外なら理由を記録する。
   - テストの妥当性: 受け入れ条件・正常系・異常系・エッジケースを過不足なく検証するか。不足は未検証の受け入れ条件・分岐・境界、過剰は重複・要件と無関係・保守コストに見合わない過度なテスト。実装内部ではなく要件・振る舞いを検証し、実際に失敗しうる検証かを確認する。
4. レビュー中はコード・テスト・Git の状態を変更しない。書き込みは `.ai/` 配下の Markdown のみ。読み取り目的のテスト実行は可。
5. 指摘の根拠を確認・重複排除し、不採用理由と受け入れ条件照合を含め `.ai/review-<n>.md` に保存する。根拠のある対応可能な指摘だけを採用し、推測は「推測」と明記、好みは除く。テンプレートの正本は `docs/review.md`。
6. **H3**: 人間だけが修正対象の `- [ ] 修正する` に `[x]` を付ける。Codex は選択しない。指摘ゼロなら修正選択は不要。

- ID はコードとテストの妥当性が `C1` 等、セキュリティが `S1` 等。テストの妥当性は観点を明記する。レビュー回数はファイル名で識別する。
- 重要度は高（不具合・脆弱性・受け入れ条件未達）、中（特定条件の問題・保守性・テストの不足や過剰、不適切な検証）、低（直す価値の明確な軽微な改善）。
- 人間は修正しない指摘に理由を書いてよい。ただし未対応指摘が残る間は指摘ゼロとは扱わず、push・Draft PR 作成へ進まない。

## 6. 指摘修正フロー（工程 8）

1. Codex は `.ai/review-<n>.md` のうち、`[x]` が付いた指摘だけを修正する。
2. チェックのない指摘には手を付けない。
3. 指摘ごとにコミットする。メッセージに ID を含める（例: `fix: C1 空入力時の例外を修正`）。
4. 修正に設計変更が必要な場合は、修正せずに止まって人間に確認する。
5. テスト全体・lint・型チェックを実行し、`.ai/report.md` に修正報告を追記する。

修正後は独立した新規セッションで再レビューし、`review-<n+1>.md` に保存する。修正差分を中心に全受け入れ条件も再確認する。H3 承認済み指摘が解消するまで、その範囲で自動反復できる。新規指摘の修正は新たな H3 を待つ。

範囲外・設計変更・依存追加や更新・要件の曖昧さや計画との矛盾・同じ問題で3回失敗した場合は停止し、「状況・選択肢・推奨案」を人間に提示する。

## 7. PR と完了（工程 9）

1. 独立レビューの指摘ゼロで、人間の個別指示を待たずに push・Draft PR を自動作成する。新規・未承認・未対応指摘が残る間は進めない。作業単位で明示された push・PR 作成禁止指示がある場合は従う。
2. PR 本文には次の内容を書く。
   - `Closes #<番号>`
   - 変更概要
   - テスト結果
   - 対応したレビュー指摘の ID
   - 対応しなかった指摘とその理由
3. マージは人間（H4）。人間が PR と検証結果を確認し、自分でマージする。Codex はマージしない。

## 人間の承認ポイント

| ID | タイミング | 人間が確認すること | 承認の残し方 |
|----|-----------|-------------------|-------------|
| H1 | Issue 作成前 | 要件・受け入れ条件・範囲外 | Codex に作成を指示する |
| H2 | 実装前 | 実装計画とテスト計画（まとめて確認） | Codex に承認を伝える → `状態: 承認済み` |
| H3 | 修正前 | どの指摘を修正するか | `review-<n>.md` に `[x]` を付ける |
| H4 | マージ前 | PR・テスト結果 | 人間が自分でマージする |

上記以外に、エージェントが止まって確認を求めたときも人間が判断する（範囲外の変更、設計変更、依存の追加など）。
