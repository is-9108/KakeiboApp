# PRをレビューする

review は自分で細かく読み込むのではなく、review-coordinator に観点別レビューを任せ、返ってきた結果を検証して投稿する。
観点別レビュー（review-spec・review-tests・review-code）は、review-coordinator がそれぞれ独立したセッションで実行し、結果を `.review/pr-<PR番号>/round-<回数>/` のmdファイルで受け取る。

## 1. 前提を集める

1. `gh pr view <番号>` でPR本文を読み、`Closes #<番号>` からissue番号を確認する
2. `gh pr view <番号> --comments` で過去のレビューコメントを読み、今回が何回目のレビューかを数える（過去の「レビュー（n回目）」コメントの数＋1）
3. 4回目になる場合はレビューせず、未解決の指摘をまとめて「人間の判断が必要」とPRコメントに書いて止まる

## 2. 実行する観点を決める

- 1回目：仕様（spec）・テスト（tests）・コード（code）の3つすべて
- 2回目以降：前回のPRコメントで「必須」の指摘に付いている観点（`[spec]` など）だけ
  - ただし、前回からの修正差分が大きい場合（`git diff <前回のコミット> refs/review/pr-<PR番号> --stat` で変更行数が100行を超える、または新しいファイルが追加された）は、code を必ず加える
  - 前回のコミットは `.review/pr-<PR番号>/round-<前回>/head.txt` にある。`refs/review/pr-<PR番号>` が古い場合は先に `git fetch origin +pull/<PR番号>/head:refs/review/pr-<PR番号>` で更新する
- 実行しない観点の「推奨」の指摘は、自分で修正差分を見て対応状況だけ確認する

## 3. review-coordinator に依頼する

サブエージェント `review-coordinator` を起動し、PR番号・issue番号・レビュー回数・実行する観点を渡す。
2回目以降は、前回の `.review/pr-<PR番号>/round-<前回>/` のパスも渡す。

review-coordinator は `summary.md` のパスと全文を返す。未完了の観点があれば、その観点は自分でレビューする。

## 4. 検証してまとめる

1. 各指摘について、示された箇所を `.review/pr-<PR番号>/src/` で自分で確認する。根拠が確認できない指摘、推測だけの指摘は捨てる
2. 重大度をつける
   - **必須**：受け入れ条件を満たさない、バグ、テスト不足。修正しないとマージできない
   - **推奨**：直したほうがよいが、マージは妨げない
3. 必須の指摘が0件なら「マージ可能」とする

## 5. 投稿する

本文を一時ファイルに書いてから投稿する。

```
gh pr comment <番号> --body-file <一時ファイル>
```

コメントの形式：

```markdown
## レビュー（<n>回目）

### 判定
修正が必要 / マージ可能

### 必須
1. [spec] `path/to/file:行` 指摘内容。根拠。修正案

### 推奨
1. [code] ...

### 受け入れ条件の確認
- [x] 条件1（確認方法）
- [ ] 条件2（満たしていない理由）

### 観点別レビュー
- 実施：<観点>（独立したセッションで実施。未完了があれば明記）
- 省略：<観点>（理由。例：前回「必須」の指摘なし）
```

各指摘の先頭には、指摘を出した観点（`[spec]`・`[tests]`・`[code]`、自分で見つけたものは `[review]`）を付ける。次回レビューで実行する観点を決めるのに使う。
指摘がない区分には「なし」と書く。コードは変更しない。マージもしない。

## 6. 後片付け

投稿したら、PRのコードを取り出した作業ツリーを消す。mdファイルは次回のレビューで使うので残す。

```
git worktree remove --force .review/pr-<PR番号>/src
```
