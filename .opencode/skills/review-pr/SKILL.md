# PRをレビューする

review は自分で細かく読み込むのではなく、観点別レビューに任せ、返ってきた結果を検証して投稿する。
観点別レビュー（仕様・テストを見る review-spec と、コードを見る review-code）は `scripts/review/run-reviewers.sh` でそれぞれ独立したセッションとして実行し、結果を `.review/pr-<PR番号>/round-<回数>/` のmdファイルで受け取る。

## やり取りするファイル

```
.review/pr-<PR番号>/
├── src/                 # PRのコード（スクリプトが git worktree で取り出す）
└── round-<回数>/
    ├── request.md       # 依頼（review が書く）
    ├── head.txt         # レビューしたコミット（スクリプトが書く）
    ├── spec.md          # review-spec の結果
    ├── code.md          # review-code の結果
    └── *.log            # 各セッションの出力
```

## 1. 前提を集める

1. `gh pr view <番号>` でPR本文を読み、`Closes #<番号>` からissue番号を確認する
2. `gh pr view <番号> --comments` で過去のレビューコメントを読み、今回が何回目のレビューかを数える（過去の「レビュー（n回目）」コメントの数＋1）
3. 4回目になる場合はレビューせず、未解決の指摘をまとめて「人間の判断が必要」とPRコメントに書いて止まる

## 2. 実行する観点を決める

- 1回目：仕様・テスト（spec）とコード（code）の両方
- 2回目以降：前回のPRコメントで「必須」の指摘に付いている観点（`[spec]`・`[code]`）だけ
  - ただし、前回からの修正差分が大きい場合（`git diff <前回のコミット> refs/review/pr-<PR番号> --stat` で変更行数が100行を超える、または新しいファイルが追加された）は、code を必ず加える
  - 前回のコミットは `.review/pr-<PR番号>/round-<前回>/head.txt` にある。`refs/review/pr-<PR番号>` が古い場合は先に `git fetch origin +pull/<PR番号>/head:refs/review/pr-<PR番号>` で更新する
- 実行しない観点の「推奨」の指摘は、自分で修正差分を見て対応状況だけ確認する
- 必須の指摘が `[review]` だけの場合は、観点別レビューを実行せず、自分で修正差分を見て確認する

## 3. request.md を書く

`.review/pr-<PR番号>/round-<回数>/request.md` を次の形で書く。

```markdown
# レビュー依頼：PR #<PR番号>（<回数>回目）

## 対象
- PR：#<PR番号>（`gh pr view <PR番号>`、`gh pr diff <PR番号>` で確認する）
- issue：#<issue番号>（`gh issue view <issue番号>`）
- 実装プラン：`.review/pr-<PR番号>/src/docs/plans/issue-<issue番号>.md`
- PRのコード：`.review/pr-<PR番号>/src/`（リポジトリ直下のコードは main なので見ない）

## 確認範囲
<!-- 1回目：「PR全体」
     2回目以降：「前回指摘の対応確認と、前回レビュー以降の修正差分」と書き、差分の確認方法を添える：
     `git diff <前回の head.txt のコミット> refs/review/pr-<PR番号>` -->

## 前回の指摘
<!-- 2回目以降は、前回のPRコメント「レビュー（<前回>回目）」の必須・推奨の指摘のうち、
     今回実行する観点（`[spec]` などの付いたもの）を写す。1回目は「なし」 -->

## 結果の書き方
- 結果は `.review/pr-<PR番号>/round-<回数>/<観点>.md` に書く（spec / code）
- 形式は各観点の skill に従い、最後の行を `<!-- 完了 -->` にする
```

## 4. 観点別レビューを実行する

```
scripts/review/run-reviewers.sh <PR番号> <回数> <観点...>
```

観点は 2. で決めたもの（`spec`・`code`）を並べる。観点別レビューが独立したセッションで並行に動き、すべて終わるまで待つ。時間がかかるので、シェルのタイムアウトは 3600000（60分）にする。

- 終了コード0：実行した観点がすべて完了
- 終了コード1：未完了の観点がある。表示されたログを確認し、原因が一時的なもの（タイムアウト、接続エラー）なら、その観点だけ一度再実行する。再実行しても未完了なら、その観点は自分でレビューする

## 5. 検証してまとめる

実行した観点の結果ファイル（`spec.md`・`code.md`）を読む。

1. 各指摘について、示された箇所を `.review/pr-<PR番号>/src/` で自分で確認する。根拠が確認できない指摘、推測だけの指摘は捨てる
2. 同じ箇所・同じ内容の指摘は1つにまとめ、観点を併記する
3. 重大度をつける
   - **必須**：受け入れ条件を満たさない、バグ、テスト不足。修正しないとマージできない
   - **推奨**：直したほうがよいが、マージは妨げない
4. 必須の指摘が0件なら「マージ可能」とする

## 6. 投稿する

本文を一時ファイルに書いてから投稿する。

```
gh pr comment <番号> --body-file <一時ファイル>
```

コメントの形式：

```markdown
## レビュー（<n>回目）

### 判定
修正が必要 / マージ可能

### 必須
1. [spec] `path/to/file:行` 指摘内容。根拠。修正案

### 推奨
1. [code] ...

### 受け入れ条件の確認
- [x] 条件1（確認方法）
- [ ] 条件2（満たしていない理由）

### 観点別レビュー
- 実施：<観点>（独立したセッションで実施。未完了があれば明記）
- 省略：<観点>（理由。例：前回「必須」の指摘なし）
```

各指摘の先頭には、指摘を出した観点（`[spec]`・`[code]`、自分で見つけたものは `[review]`）を付ける。次回レビューで実行する観点を決めるのに使う。
指摘がない区分には「なし」と書く。コードは変更しない。マージもしない。

## 7. 後片付け

投稿したら、PRのコードを取り出した作業ツリーを消す。mdファイルは次回のレビューで使うので残す。

```
git worktree remove --force .review/pr-<PR番号>/src
```
