# PRを作る

## 作る前に

1. 全テストを実行し、すべて通ることを確認する。失敗したテストがあればPRを作らずに直す。テストを実装に合わせて弱めない
2. プラン（`docs/plans/issue-<番号>.md`）のテストケース一覧のIDが、すべてテストコードになっているか確認する
3. 変更をcommitし、作業ブランチをpushする（`git push -u origin <ブランチ>`）。`main` にはpushしない
4. commitの件名は `feat:` などの接頭辞のあとを日本語にする

## 本文を書く

`.github/pull_request_template.md` の見出しをそのまま使う。見出しを足したり削ったりしない。`<!-- -->` のコメントは消し、書くことがない見出しには「なし」と書く。

| 見出し | 書くこと |
| --- | --- |
| 概要 | 何をしたかを1〜3行で |
| 関連 Issue | `Closes #<番号>` |
| 受け入れ条件の充足 | issueの受け入れ条件をそのまま写し、満たしたものにチェック |
| 変更内容 | ファイルごとの変更点 |
| テスト | 実行したコマンドと結果（成功数・失敗数）をそのまま貼る |
| テストの変更 | 追加・変更・削除したテストと、プランのテストIDとの対応 |
| レビュー（review エージェント） | 初回は「未レビュー」 |
| 仕様の確認 | 設計（docs/）と食い違う点、確認が必要な点 |
| 設計判断（ADR） | プランにない設計判断とその理由 |
| プランからの逸脱 | プランと違う実装をした箇所と理由 |
| レビューで特に見てほしい点 | 自信がない箇所 |
| 既知の制約 | 未対応の点、後続issueに回したもの（issue番号） |

## 作成する

```
gh pr create --base main --title "<日本語のタイトル>" --body-file <一時ファイル>
```

PRのURLを報告する。マージはしない。

## レビュー指摘の修正後（fix エージェント）

1. 指摘ごとに修正し、全テストを実行して通ることを確認してからpushする
2. 「レビュー（review エージェント）」の見出しに、往復回数と各指摘への対応（修正した／対応しない理由）を書く。ほかの見出しも変更があれば更新する
3. `gh pr edit <番号> --body-file <一時ファイル>` で本文を更新し、対応内容をPRコメントで報告する（`gh pr comment <番号> --body-file <一時ファイル>`）
