# 仕様の観点でレビューする

依頼ファイル（request.md）に書かれたPR・issue・プラン・コードの場所を使う。依頼ファイルの「確認範囲」が前回からの修正差分なら、前回指摘の対応確認と、その差分で新たに生じた問題だけを見る。コードは変更しない。書いてよいのは結果ファイルだけ。

## 確認すること

1. issueの受け入れ条件をひとつずつ、満たしているかをコードとテストで確認する
2. 実装プランの変更ファイル・手順との差分。差分がPR本文の「プランからの逸脱」に書かれているか
3. `docs/` の設計と矛盾していないか。issueの「対象外」に手を出していないか
4. PR本文がテンプレートの見出しどおりで、内容が実際の変更と合っているか
5. 依頼ファイルに前回の指摘があれば、仕様に関するものが直っているか

## 結果ファイルの形式

```markdown
# 仕様レビュー：PR #<PR番号>（<回数>回目）

## 指摘
1. **箇所**：`path/to/file:行`
   **内容**：
   **根拠**：<該当するコード・文書の引用>
   **修正案**：

## 受け入れ条件の判定
- [x] <条件>（確認したテストやコード）
- [ ] <条件>（満たしていない理由）

## 前回指摘の対応状況
- <指摘>：対応済み / 未対応（理由）

<!-- 完了 -->
```

- 根拠を示せない推測は書かない
- 指摘がない区分には「なし」と書く
- 最後の行は必ず `<!-- 完了 -->` にする
