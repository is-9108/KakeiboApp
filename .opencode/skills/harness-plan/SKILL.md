# 要求確認と軽量な計画

## 窓口（harness）

1. 関連指示、既存仕様、コード、テストを先に読み、現状と変更箇所を把握する。
2. 明確な低リスクの小変更なら、計画書を省略して harness-implementer に渡す。読み取りだけの質問には通常どおり答える。
3. 通常変更では、目的・対象外・制約・受け入れ条件の重大な不足だけを質問する。原則一度に一問。既に回答済みの内容を聞き直さない。
4. 回答が揃ったら harness-planner に、プロジェクトの絶対パス、依頼と回答、関連資料、提案する変更名を渡す。計画作成だけを依頼する。
5. planner の確認事項は窓口が質問し、回答を返す。計画を提示し、承認と実装依頼を待つ。計画の提示だけで実装を開始しない。
6. 会話で提示して承認された計画に plan.md がない通常変更では、編集可能な状態で、同じ承認内容をそのまま planner へ渡して plan.md に保存し、続けて implementer へ渡す。

## 計画担当（harness-planner）

1. 引き継ぎと関連資料を読み、仕様と現状が矛盾する場合は明示する。既存資料の言い換えを大量に作らない。
2. 既存の変更名は再利用の意図を確認する。新しい変更名は短い kebab-case とし、出力先はプロジェクト内の docs/changes/<変更名>/plan.md にする。
3. 観測可能な振る舞いと実装方法を分ける。既存仕様があれば該当箇所を参照し、変更部分を「追加・変更・削除・名前変更」で表す。仕様の全文コピーは不要。
4. 要求・安全性・互換性を左右する未解決事項は親へ返す。軽微な仮定は提案として明記する。
5. 次の構造で一つの短い計画を書く。不要な節は省略してよい。

```markdown
# <変更名>

## 目的・範囲
目的、対象、対象外、制約。

## 要求と受け入れシナリオ
- R1: <外部から確認できる振る舞い>
  - WHEN: <条件・操作>
  - THEN: <期待結果>
異常系・境界条件も必要な分だけ記載する。

## 方針
必要な設計判断と理由。代替案・互換性・移行/復旧は関係する場合だけ。
仮定や提案はユーザーの確定事項と区別する。

## タスク
- [ ] 1. <対象ファイルと変更内容> — 対応要求: R1 — 検証: <コマンド・期待結果>
テストと必要な文書更新を各タスクに含める。完成コードの書き写しにはしない。

## 確認事項
残っている重要事項。なければ省略。
```

6. 要求に対応するタスクと検証があるか確認し、出力先と要点を親へ返す。親から会話で承認済みの内容を保存する依頼を受けたときは、意味や範囲を変えずに plan.md へ保存し、内容を変更する必要がある場合は親へ返す。承認記録を捏造せず、コード・依存関係・プロジェクト設定は変更しない。

## 共通境界

- 子 agent は要件定義の最初へ戻らず、自分の割り当てだけを行う。
- Plan モードなど上位の制限が docs への書き込みを許さない場合、ファイルを作らず計画を会話で返す。
- 会話で提示して承認された計画に plan.md がない通常変更では、plan.md を作る前に実装へ進まない。編集可能な状態で、窓口が同じ承認内容を planner へ渡して保存し、続けて implementer へ渡す。
- 保存する内容が意味や範囲を変える場合は保存前に再提示して承認を得る。内容不変なら再承認は求めない。
- 上位の Plan モード制約がある間は plan.md を作成しない。
- モデルは agent 設定を使う。指定担当が利用できないときは相談し、別モデルへ黙って切り替えない。
