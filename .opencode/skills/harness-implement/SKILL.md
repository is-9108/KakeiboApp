# 実装・テスト・修正

## 窓口からの引き継ぎ

通常変更は承認された plan.md を読み、harness-implementer に次を渡す。

- プロジェクトの絶対パス、依頼と承認範囲。
- 計画の絶対パスと今回のタスク。小変更では具体的な対象と期待結果。
- 保護する既存差分、関連ファイル、検証コマンドが分かればその内容。

会話で提示して承認された計画に plan.md がない通常変更では、窓口が同じ承認内容を planner へ渡して plan.md に保存したうえで implementer へ渡す。保存で意味や範囲を変える場合は保存前に再提示して承認を得る。内容不変なら再承認は求めない。

実装担当は追加 agent を起動しない。不足や範囲外の問題は親へ返す。

## 実装担当の手順

1. 関連コード・テスト・指示と既存差分を確認する。再開時は plan.md のチェックと実コードを照合し、完了済み作業を無条件に繰り返さない。
2. プロジェクトで定義されたテスト・lint・型検査等を確認する。コマンドを推測せず、基準の失敗があれば記録する。依存インストールを無断で行わない。
3. 不具合は症状を再現し、エラーと関連変更を確認する。一つの原因仮説を最小の検証で確かめ、推測で修正を重ねない。
4. 振る舞いの変更は原則 RED → GREEN → 必要な整理の順で進める。
   - 期待する振る舞いをテストにする。
   - 実行して期待した理由で失敗することを確認する。
   - 最小限の実装で通し、関連する回帰テストを行う。
   - 設定・文書・生成物などテスト先行が不適切なら、適切な検証方法と理由を報告する。テスト基盤がなく確認できない場合は親へ相談する。
5. ユーザーの既存コードや先に書かれたコードを TDD の形式のために削除しない。スコープ外のリファクタリングを混ぜない。
6. 承認済みの範囲を超える要件変更、公開APIの変更、依存の追加、移行が必要になったら止めて親へ返す。承認済みの範囲内の判断では追加の質問で止まらず、進めて検証する。同じ問題への修正が2回失敗したら、原因と試行内容を整理して設計担当への相談を求める。
7. 対象の検証を実行し出力と終了コードを読む。完了前にプロジェクトで必要な全体検証も実行する。実行不能・既存失敗を隠さず、部分的な成功を全体合格としない。
8. 対応要求が満たされ検証できたタスクだけ plan.md のチェックを更新する。文書作成・大幅更新は内容を親へ渡し writer に依頼する。親から writer の内容案と適用先・範囲の指示を受け取った場合だけ、docs/ 外の承認済み配置（README.md、AGENTS.md、skills など）への新規作成・更新を限定して反映できる。設定や実行コードを含む内容は適用時に機能検証し、範囲や仕様が変わる場合は親へ戻す。

## 親への報告

- 状態: 完了 / 確認が必要 / ブロック。
- 変更ファイルと実装した要求・タスク。
- 実行コマンド、終了コード、結果。テスト先行なら RED と GREEN の結果。
- 失敗、未検証、仮定、計画との差異。
- 必要な文書更新とレビュー対象。

窓口は通常変更で harness-review を使う。明確な小変更では独立レビューと文書を省略できるが、検証結果は会話で報告する。担当モデルが利用できない場合は自己作業で代替しない。
