# 実装プランを書く

## 準備

1. `gh issue view <番号>` でissueを読む。受け入れ条件・対象外・依存を確認する
2. 「背景・関連する設計」に挙がった `docs/` の設計を読む
3. 変更対象になりそうな既存コードとテストを読む
4. 受け入れ条件が曖昧、または設計と食い違う場合は、プランを書かずに人間に質問する

## プランのひな形

`docs/plans/issue-<番号>.md` に次の見出しで書く。書くことがない見出しには「なし」と書く。

```markdown
# issue-<番号> <issueのタイトル>

## 概要
<!-- 何をどう実装するかを3行以内で -->

## 受け入れ条件との対応
| 受け入れ条件 | 満たす方法 | 検証するテストID |
| --- | --- | --- |

## 変更するファイル
| ファイル | 新規/変更/削除 | 変更内容 |
| --- | --- | --- |

## 手順
<!-- テストを先に書く順番で。1手順＝1コミットの大きさ -->
1.

## テストケース一覧
| ID | 種別 | 対象 | 前提・入力 | 期待結果 |
| --- | --- | --- | --- | --- |
| T1 | 正常系 | | | |
| T2 | 異常系 | | | |
| T3 | 境界値 | | | |

## 対象外
## 確認事項・リスク
```

## テストケースの書き方

- 種別は「正常系」「異常系」「境界値」のどれか。3種類とも最低1つずつ入れる
- すべての受け入れ条件に、それを検証するテストを1つ以上対応させる
- 期待結果は具体的な値や状態で書く（「エラーになる」ではなく「`ValidationError` を返し、保存されない」）
- 境界値は、上限・下限・ちょうどの値・1つ外れた値を検討する（金額0、負数、最大桁、空文字、月末日など）
- implement エージェントはこの表をそのままテストコードにする。実装に依存しない書き方にする

## 仕上げ

1. プランを書いたら、issueの「実装プラン」欄をプランのパスに更新する（`gh issue edit <番号> --body-file <一時ファイル>`。ほかの見出しは変えない）
2. プランのパスと、確認事項があればそれを報告する
