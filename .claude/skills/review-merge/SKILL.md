# レビューのマージ（review-merge）

`CLAUDE.md` の「独立レビュー」「セキュリティレビュー」「レビュー結果の報告」を、1 回の操作で行うための手順。

## 守ること

- レビュー中は、コード・テスト・Git の状態を変更しない。書き込んでよいのは `.ai/` 配下の Markdown だけ。テストの実行など、読み取り目的のコマンドは使ってよい。
- `/code-review` の `--fix` と `--comment` は使わない。
- 判断の材料は、Issue、`.ai/plan.md`、`.ai/report.md`、`main` との差分だけにする。報告の内容は、コードで確認してから採用する。
- 根拠のある、対応可能な指摘だけを書く。推測の場合は「推測」と明記する。好みの問題は指摘しない。
- チェックボックスは付けない。どの指摘を修正するかは人間が決める（H3）。

## 手順

### 1. 判断材料を集める

1. Issue 番号を決める。引数があればそれを使う。なければ、`.ai/plan.md` の Issue の URL から読む。
2. 次のものを読む。
   - `gh issue view <番号>`
   - `.ai/plan.md`
   - `.ai/report.md`
3. 差分を確認する。
   - 変更がコミットされていない場合もあるので、`git log --oneline main..HEAD`、`git status --short`、`git diff main --stat` の 3 つを実行する。
   - 追跡されていない新規ファイルも、レビューの対象に含める。
4. 出力先の番号 `<n>` を決める。`.ai/review-*.md` の既存の最大の番号に 1 を足す。1 つもなければ 1 にする。

### 2. 2 つのレビューを独立して並行実行する

Agent ツールで、サブエージェントを 2 つ、1 つのメッセージで同時に起動する。

- `subagent_type` は `general-purpose` にする。会話履歴を引き継ぐ `fork` は使わない。これまでの会話が判断に混ざらないようにするため。
- 2 つのサブエージェントに、それぞれ次の内容を渡す。
  - **共通**:
    - リポジトリのパス、ブランチ、Issue 番号
    - 判断材料のパス（`.ai/plan.md`、`.ai/report.md`）
    - 「コード・テスト・Git の状態を変更しない」こと
    - 「Skill ツールが使えない場合は、同じ観点で手動でレビューする」こと
  - **差分の扱い**:
    - 変更が未コミットだと、Skill が自動で集める差分が空になることがある。
    - その場合は、`git diff main` と、追跡されていないファイルの内容を自分で読んで、レビューの対象にする。
  - **セキュリティ担当**:
    - Skill ツールで `security-review` を実行する。
    - 結果を `.ai/review-<n>-security.raw.md` に保存し、同じ内容を返す。
  - **コード担当**:
    - Skill ツールで `code-review` を実行する（`--fix` と `--comment` は付けない）。
    - Skill がバックグラウンドで動く場合は、完了するまで待ってから結果を受け取る。
    - 結果を `.ai/review-<n>-code.raw.md` に保存し、同じ内容を返す。
- 2 つが両方とも終わるまで待つ。結果を予想して先に進まない。

### 3. 指摘を検証してマージする

1. 2 つの結果のすべての指摘について、該当するコードを自分で読み、事実かどうかを確かめる。
2. 同じ問題を指している指摘は、1 件にまとめる。
3. 各指摘を、「採用する」か「採用しない」かに分ける。次のどれかに当てはまる指摘は採用せず、理由を付けて「採用しなかった指摘」に書く。
   - Issue の決定事項や、承認済みの計画で決めた設計どおりのもの
   - 起きる経路をコードで確認できないもの（将来の変更を想定した指摘など）
   - 好みの問題、または計画の範囲を超えるリファクタリングの提案
   - Issue の範囲外のもの
4. 採用した指摘に、重要度（高・中・低）と ID（`R<n>-<連番>`）を付ける。
   - 高: 受け入れ条件を満たしていない。または、正しく動かない。
   - 中: 特定の条件で問題が起きる。または、テストが要件を検証できていない。
   - 低: 動作は正しいが、直す価値がはっきりあるもの。
5. セキュリティの指摘は、`/security-review` の基準（確度 8 以上）を満たすものだけを採用する。
6. 受け入れ条件を 1 項目ずつ、差分と report の検証結果で確認する。あわせて、計画にない変更や、Issue の範囲外の変更がないかも確認する。

### 4. 結果を保存する

下のテンプレートで `.ai/review-<n>.md` に書く。生の結果のファイル（`*.raw.md`）は、根拠として残す。

### 5. チャットで報告する

重要度ごとの件数と、ファイルのパスだけを伝える。未検証の受け入れ条件があれば、それも 1 行で伝える。

## テンプレート

```markdown
# Issue #<番号> レビュー結果（<n> 回目）

- 対象: `main` との差分（ブランチ `<ブランチ>`、<日付> 時点。未コミットならそう書く）
  - <変更ファイルの一覧>
- 判断材料: Issue #<番号>、`.ai/plan.md`（<状態>）、`.ai/report.md`、`main` との差分
- 実施したレビュー:
  - `/code-review`（独立したサブエージェントで実行。生の結果: `.ai/review-<n>-code.raw.md`）
  - `/security-review`（独立したサブエージェントで実行。生の結果: `.ai/review-<n>-security.raw.md`）
  - `CLAUDE.md` の観点による手動確認
- どの指摘を修正するかは人間が決める（H3）。チェックボックスは人間が付ける。

## サマリ

| 重要度 | 件数 |
|---|---|
| 高 | 0 |
| 中 | 0 |
| 低 | 0 |
| セキュリティ | 0 |

<受け入れ条件を満たしているかどうかを、1〜2 文で書く>

## 指摘

### R<n>-1 [<重要度>] <見出し>

- [ ] 修正する
- 場所: `<ファイル>:<行>`
- 内容: <何が問題か>
- 根拠: <コードや資料のどこで確認したか。推測なら「推測」と明記する>
- 影響: <どんな入力や状態で、何が起きるか>
- 推奨対応: <どう直すか。コードそのものは書かない>

## 受け入れ条件の確認

| 受け入れ条件 | 結果 | 根拠 |
|---|---|---|

計画との一致: <計画にない変更、Issue の範囲外の変更の有無>

## 確認事項（指摘ではない）

- <未実施の検証、人間が行う作業など>

## セキュリティレビュー

対象にした理由（対象外ならその理由）: <理由>

結果: <件数と、確認した観点>

## 採用しなかった指摘

| 指摘 | 出どころ | 採用しなかった理由 |
|---|---|---|
```
